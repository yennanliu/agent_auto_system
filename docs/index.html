Architecture

Non-blocking by design

The API returns 202 immediately; flows run in a registered asyncio task so any run can be cancelled mid-flight.

Live, cheap streaming

/stream polls the DB every 0.5 s; append_log uses json_insert to append atomically — no read-modify-write.

No @CrewBase

The decorator's id(self) memoize serves stale LLMs after GC reuses addresses. Crews are plain classes, rebuilt each run.

normalize vs. resolve

normalize() picks (provider, model) with no API call; resolve() builds the LLM only when a crew needs it.

Resilient startup

reconcile_stale_runs() marks orphaned running/pending rows as failed on every boot.

Scales down and up

SQLite for a single node; point DATABASE_URL at Postgres for production — same code, same migrations.

The harness layer

A control plane between the executor and CrewAI

One layer sits between the app and the AI and handles everything repetitive and error-prone — choosing the model, retrying on failure, scoring the result, and adding up the cost — so the rest of the code stays clean. Six jobs, one tidy seam.

Pick your AI, per task

Choose OpenAI, Anthropic Claude, or Google Gemini right from the screen. normalize() resolves the model without an API call; resolve() builds the crew's LLM at a task-specific temperature.

Fixes its own mistakes

A validator checks every result. If it fails, the system re-runs the task with the previous error handed back to the AI — so it corrects itself on the next attempt.

Falls back automatically

If one model is briefly down (503, 429, timeouts), the system quietly tries a sibling model with backoff — up to 5 attempts. Real errors stop right away.

Grades every result

A separate AI scores each result from 0–100 with a confidence level — never the same model that produced it. Per-task rubrics ground the score; a simple fallback keeps it honest.

Tracks tokens & cost

Every run records the provider, model, tokens in/out, retry count, quality score, and estimated cost in USD. /api/stats adds it all up in a single database pass.

Shows you what's happening

Watch progress update every half-second, check a rich /health endpoint, and turn on optional per-run Langfuse traces — all of which fail softly and never break a run.

How a run works

Trigger, run, check, and score

The moment you hit run, you get confirmation the work has started — then you watch each step happen live, from the first click to the final score.

1

Create & trigger

POST /api/jobs stores your inputs; /run starts a background task and confirms instantly.

2

Choose the AI

The system settles on the provider/model and hands the task to the right workflow.

3

Do the work

The AI crew runs its tools and produces structured data. A brief outage falls back to another model.

4

Check it

A rule checks the result. If it's off and retries remain, the task re-runs with the error explained.

5

Score it

A separate AI grades quality 0–100. It's purely for your information — it never overrides success.

6

Save & show

Tokens, cost, retries, and the score are saved in one write; the final status streams straight to your screen.

Guide

From zero to your first scored run

Download it, add a single AI key, and run a real automation in a few minutes — then learn to schedule, track, and administer it. Every step below uses real screenshots of the running app.

1Set up & launch 2Run your first automation 3Track, retry & schedule 4Administer & explore
1

Set up & launch

1

Download and install

Dependencies are managed with uv. The Playwright step is only needed for browser-driven tasks (form fill, Shopee, X, Tasker, email collector).

$ git clone https://github.com/yennanliu/agent_auto_system
$ cd agent_auto_system
$ uv sync                                # install deps
$ uv run playwright install chromium     # for browser jobs
2

Add at least one AI key

Copy the sample settings file and fill in an OPENAI_API_KEY, ANTHROPIC_API_KEY, or GEMINI_API_KEY — any one is enough to start. Keys can also be stored (encrypted) later from the Admin page.

$ cp .env.example .env
$ # edit .env → set OPENAI_API_KEY=sk-… (or ANTHROPIC / GEMINI)
3

Start the server

Run the app and open it in your browser. Running the tests is a good first sanity check.

$ uv run uvicorn src.main:app --reload --port 8000
$ open http://localhost:8000
4

Sign in

The app requires a login. On first startup an admin account is created for you — sign in with admin / admin.

⚠️Change this before putting the app online. The default account is only created while the users table is empty; afterwards, manage users and passwords from the Admin page.
2

Run your first automation

We'll run the Hacker News Digest — no external accounts needed, just an AI key. It reads the top HN stories and returns a themed, structured summary.

1

Open "+ New Run" and pick an automation

The picker lists every built-in task type. Choose HN Digest. Each tile swaps in its own form below.

2

Fill the form and choose a model

Set Number of Stories to 5, then pick a provider and model. This demo uses OpenAI · gpt-4o-mini — fast and cheap. Each task carries its own temperature under the hood.

3

Watch it run — live

Hit Run ▶ and you land on Activity. A half-second SSE stream lights up the step graph in order — Start → Validate → Fetch → Digest → Verify → Evaluate → Done — and appends log lines as they happen. Each node turns green as it completes and shows how long it took.

🔁The Validate and Verify steps are the self-check: a rule inspects the output and, if it fails while retries remain, the task re-runs with the error handed back to the AI. A brief provider outage (503/429) silently falls back to a sibling model — you don't lose the run.
4

Read the scored result

When the run finishes, click the row to expand it. The Result tab holds the structured JSON; Flow shows the step timeline, Log the full stream, and Usage the model, tokens, and estimated cost. Copy JSON lifts the whole result to your clipboard. The green ★ badge is the independent judge's score.

✅This exact run: hacker_news_digest on gpt-4o-mini — finished in 21 s, passed validation, and was scored 100/100 by an independent judge model (never the one that wrote the answer).
3

Track, retry & schedule

A few runs in, the operational side comes alive: browse history, compare runs at a glance, and put a job on a cron so it runs itself.

1

Browse run history & retry failures

The Activity table lists every run with its status, who ran it, the provider, a ★ quality score, duration, and a result preview. Filter by automation, status, or date. A low score doesn't mean failure — the run still succeeded; the score is your signal to double-check. Any failed run gets a one-click ↺ Retry that hands the previous error back to the AI.

2

Compare runs on the Overview grid

The Overview tab is an Airflow-style grid: pick an automation and every run becomes a column, every step a row. Green is success, red failed, blue running, grey pending. Click any cell to jump to that step's log — perfect for spotting exactly where a run went sideways.

3

Schedule it to run automatically

Add a cron expression in the New Run dialog (or the presets dropdown) and the job is saved instead of run once — the built-in scheduler fires it on time, in UTC. The Schedules tab shows each job's cron, next fire time, run count, and last result, with Run now, Edit, and Unschedule controls.

4

Administer & explore

The Admin and System tabs are where you manage people, keys, and which tasks are live — and see exactly how each automation is wired.

1

Create users & scope their permissions

Under Admin → Users, add teammates and choose exactly which automations each may run (or make them an admin). Accounts can be disabled, have passwords reset, or be deleted — and the app refuses to remove the last active admin.

2

Store API keys, encrypted

Rather than editing .env, paste provider keys under Admin → LLM Keys. They're stored Fernet-encrypted and only decrypted at run time, overriding the environment. Each provider shows a configured / not set badge, whether the value came from env, and a masked preview.

3

Toggle tasks & pick the judge model

The Automations tab is the master switch: a disabled task can't be created or run by anyone, admins included. Under Verification LLM you choose the independent judge model — kept separate from the models that produce results, so scores stay honest.

4

Inspect the System catalog & Analytics

The System tab exposes every agent, tool, crew, and workflow — roles, goals, backstories, and the real source config — so you can see how an automation is built without reading the repo. The Analytics tab totals runs, success rate, average score, tokens, and estimated cost, plus an eval-trust panel (independent-judge rate, retry/fallback rate, validation pass).
